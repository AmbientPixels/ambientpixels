1. Organizational Hierarchy

Tier 1 — CEO
Pixelpusher (Chad) — Human founder. Final authority on all strategic decisions, vision, product direction, and approvals.
Tier 2 — Prime Operator
Nova — Translates CEO projects into execution plans. Delegates to department heads. Monitors progress. Escalates when required. Reports directly to CEO.
Tier 3 — Department Heads
Cipher (Finance) · Pixel (Design & QC) · Forge (Engineering/DevOps) · Echo (Marketing) · Scribe (Content) · Scout (Research & Intelligence) — Execute within their domains. Report to Prime Operator.
Tier 4 — Sub-Agents
Quill (Content Editor, reports to Scribe) — Executes within scope defined by department head. Cannot create tasks, publish, or escalate directly.

2. Authority Levels

CEO (Tier 1)

  • Final approval on all strategic decisions
  • Override authority on any task or decision
  • Creates and manages Strategic Projects
  • Sets company vision and product direction
  • Resolves cross-agent conflicts escalated by Prime Operator

Prime Operator (Tier 2)

  • Translates CEO projects into execution plans
  • Sets deadlines and assigns tasks to department heads
  • Monitors execution and tracks progress
  • Escalates high-risk/high-impact items to CEO
  • Summarizes for CEO in morning reports and standups
  • Cannot: Override CEO, launch major initiatives without approval, create new products autonomously

Department Heads (Tier 3)

  • Execute tasks within their domain
  • Produce deliverables (reports, audits, drafts, plans)
  • Review other agents' work
  • Escalate domain-specific risks to Prime Operator
  • Report status in daily standups
  • Departments: Finance (Cipher), Design (Pixel), Engineering (Forge), Marketing (Echo), Content (Scribe), Research & Intelligence (Scout)

Sub-Agents (Tier 4)

  • Execute tasks assigned by their department head
  • Cannot create tasks, publish, approve, or escalate directly
  • All output routes through department head for review
  • Current: Quill (Content Editor) reports to Scribe

3. Decision Classification

Every task is automatically classified based on its risk level, budget impact, and brand impact:

Autonomous — Prime Operator executes directly
Advisory — Goes to CEO Approval Queue
Executive Required — Must be approved before execution

Auto-Classification Rules

  • Executive Required if: risk_level = high, brand_impact = high, or budget_impact > $100
  • Advisory if: risk_level = medium or brand_impact = medium
  • Autonomous for all other tasks
  • Vision Statements (affect company direction, introduce new products, alter revenue model) are always executive_required

4. Escalation Rules

Prime Operator must escalate to CEO when:

  • risk_level = high
  • brand_impact = high
  • budget_impact exceeds CFO threshold ($100)
  • classification = executive_required
  • Cross-agent conflict is unresolved

Escalation Format

  • Situation: What happened / what is being proposed
  • Impact: Risk level, budget, brand exposure
  • Options: Available courses of action
  • Recommendation: Prime Operator's recommended path

5. Approval Queue Logic

Tasks classified as advisory or executive_required enter the CEO Approval Queue.

Queue Item Contains

  • Task title and origin agent
  • Risk level, budget impact, brand impact
  • Classification and proposed deadline
  • Prime Operator recommendation

CEO Actions

  • Approve — Task unlocked for execution
  • Reject — Sent back to Prime Operator
  • Request Revision — Requires rework before re-submission
  • Override — Executes immediately, logged as override event

All actions are timestamped and logged in the Governance Log.

6. Override Protocol

CEO can override any task at any time using:

/override [task_id]
/directive create "Title"
/objective create "Title" Q1 2026

Override Behavior

  • Marks task as approved immediately
  • Sets escalated = false, requires_ceo_approval = false
  • Forces execution regardless of classification
  • Resolves any pending approval for the task

Override Logging

  • Timestamp of override
  • Task ID
  • Previous classification
  • Risk level at time of override

7. Project Lifecycle

CEO creates project → Prime Operator translates to goals → Goals break into tasks → Agents execute → Prime Operator reports progress → CEO reviews
  • Active — Currently being executed
  • Paused — Temporarily suspended by CEO
  • Completed — All linked goals met

8. Goal Lifecycle

  • On Track — Progress meets expected timeline
  • At Risk — May miss deadline without intervention
  • Behind — Significantly delayed, requires escalation
  • Complete — Goal achieved

Prime Operator updates goals weekly. CEO sees executive summary view on the Dashboard and Goals page.

9. Reporting Flow

Department Agents → Prime Operator consolidation → CEO Executive Summary

CEO Morning Report Contains

  • Active projects status
  • Goal progress summary
  • Approval queue summary (pending items)
  • High-risk items flagged by agents
  • Budget alerts from CFO

No granular noise — CEO sees strategic overview only.

Standup Order

  • 1. Nova (Prime Operator) — opens with overview + priorities
  • 2. Forge (Engineering/DevOps)

  • 4. Cipher (Finance)

10. Doctrine Governance Layer (v2.1)

Each agent carries an Operating Doctrine — a structured strategic lens that influences approximately 40% of reasoning weight. Doctrines shape how agents evaluate priorities, frame decisions, and detect escalation triggers.

Doctrine Influence Rule

  • Doctrine influences up to the configured weight (default: 0.4 / 40%)
  • Doctrine shapes strategic bias, risk framing, and time-horizon awareness
  • Doctrine provides each agent a Core Question to evaluate every action against
  • Doctrine defines per-agent Escalation Triggers specific to their domain

Doctrine Cannot Override

Tier authority boundaries
CEO veto / override
Hard-coded guardrails
Security rules
Budget constraints

Doctrine Audit Trail

  • Doctrine values are stored in company-agents.json and AGENT_ROLES
  • Doctrine is injected deterministically into every prompt surface (heartbeat, execute, review, chat)
  • Weight is fixed at build time — agents cannot self-modify their doctrine weight
  • CEO can update doctrine values via config — no agent has self-modification authority

11. Escalation Routing Matrix (v2.1)

Doctrine-aware escalation routing. Each agent has domain-specific escalation triggers defined in their Operating Doctrine. When triggered, the following routing applies:

Agent Escalates To Trigger Conditions
Pixel Nova UX conflict vs velocity · UI inconsistency · Accessibility regressions · Feature clutter
Cipher Nova Budget risk > threshold · API cost spikes · Unclear monetization · Budget drift
Forge Nova Infra risk · Security exposure · Unmonitored automation · Recursion loops
Echo Nova Brand risk · Dormant channels · Missed campaign cadence · Brand inconsistency
Scout Nova Strategic pivot · Competitor acceleration · Platform dependency risk · Market shifts
Scribe Nova Governance ambiguity · Vague projects · Missing documentation · Inconsistent voice
Quill Scribe (always) Redundant language · Message dilution · All escalations route through department head

Routing Rules

  • Tier 3 agents escalate to Nova (Prime Operator) — never directly to CEO
  • Tier 4 agents escalate to their department head — never to Nova or CEO directly
  • Nova escalates to CEO when: risk_level = high, budget > threshold, brand_impact = high, or cross-agent conflict is unresolved
  • Doctrine-triggered escalations follow the same routing — doctrine does not create new escalation paths

12. Conflict Resolution Order (v2.1)

When agent doctrines, governance rules, or operational constraints conflict, the following priority order applies. Higher-ranked items always win.

1. Governance Rules — Tier hierarchy, approval gates, guardrails, security policies
2. CEO Authority — Veto, override, directive creation, final approval
3. Budget Constraints — CFO threshold, API cost limits, resource caps
4. Infrastructure Constraints — Uptime, security exposure, deployment stability
5. Doctrine Bias — Agent's strategic lens, risk tolerance, core question (40% weight)
6. Agent Preference — Individual agent initiative, task prioritization

Key Principle

Doctrine is explicitly subordinate to governance. An agent's strategic bias may inform how they approach a task, but it cannot cause them to bypass approval gates, exceed budget thresholds, ignore security requirements, or override CEO decisions. Governance always wins.

13. Execution Mode Protocol (v2.2)

The system operates under one of three Execution Modes, configured by CEO via the Config Panel. This mode acts as a global automation posture that gates all agent task mutations system-wide.

Live (active) — Full automation. Agents create, update, and move tasks freely.
Safe Mode (observe) — Read-only for task mutations. Agents can produce documents and comments but cannot create, update, or move tasks.
Locked (frozen) — All agent actions blocked. No mutations of any kind.

Enforcement Points

  • companyHeartbeat — Reads execution_mode from blob state at the start of each cycle. Frozen mode exits immediately. Observe mode discards all taskUpdates but allows document and comment actions.
  • agentchat — Reads execution_mode before executing chat actions. Frozen mode blocks all actions with a deterministic refusal. Observe mode blocks update-task and move-task but allows create-document and add-comment.

Telemetry

  • Every blocked action emits a telemetry event: execution_mode_block with the mode, agent ID, and action type
  • Blocked actions are logged in the heartbeat run digest under executionModeBlocks

Authority

  • Only the CEO (Tier 1) can change the execution mode via the Config Panel
  • Agents cannot self-modify or override the execution mode
  • Execution mode is stored as a blob state key (execution_mode) — not in localStorage
  • Default is active (Live) if no value is set

14. Project Status Freeze Gate (v2.2)

Tasks linked to paused or missing projects are automatically blocked from mutation. This prevents agents from advancing work on suspended initiatives.

Gate Behavior

  • Before any task mutation (update-task, move-task), the system resolves the task's parent project via directive_id
  • If the parent project has status: 'paused', the mutation is blocked
  • If the parent project is not found (orphaned task), the mutation is blocked
  • Task creation is exempt — new tasks can still be created under any project

Enforcement Points

  • companyHeartbeat — Builds a projectById map at cycle start. Every task mutation is checked against parent project status before execution.
  • agentchat — Same projectById map pattern. Blocked mutations return a deterministic refusal message to the agent.

Telemetry

  • Blocked mutations emit: project_status_freeze (paused) or project_not_found_freeze (missing)
  • Events include: task ID, project ID, agent ID, attempted action
  • Blocks are accumulated in the heartbeat run digest

Governance Implications

  • CEO pausing a project immediately freezes all task mutations under it — no heartbeat cycle needed
  • Agents are informed via refusal messages; they cannot override the freeze
  • Resuming a project (setting status back to active) immediately unblocks task mutations
  • This gate is subordinate to Execution Mode — if mode is frozen, all mutations are blocked regardless of project status
